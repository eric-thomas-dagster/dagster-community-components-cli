# Reading a component correctly, and writing its YAML

## A component's README has two tables — only one of them is ground truth

Most component READMEs follow this shape:

```
# `SomeComponent`
<one-line description>
> callout: a real gotcha or subtlety
## When to use
## Prerequisites
## Pairs with          (companion resources/components, read-side counterparts, etc.)
## Configuration       <- hand-written summary table, can be STALE or abbreviated
[//]: # (FIELDS:START - auto-generated by tools/regen_readme_fields.py)
## Fields
### Required
### Connection / Execution / Catalog metadata / Partitions / Other
[//]: # (FIELDS:END)
```

**The `## Configuration` section (if present) is hand-written and can drift out of sync with the real schema.** The `## Fields` section between the `FIELDS:START`/`FIELDS:END` markers is mechanically regenerated from `schema.json` by `tools/regen_readme_fields.py` — it is always current and is the one to trust. When the two disagree (a field in `## Configuration` missing from `## Fields`, or vice versa), trust `## Fields` / `schema.json`, and treat the discrepancy itself as a signal the component's hand-written prose needs a PR, not as something to silently resolve in your head.

Best practice, in order: read `## Fields` (or run `dagster-component schema <id>`) for the authoritative field list → read `## Configuration`/prose for *why* a field exists and its gotchas → write YAML using only field names you saw in `## Fields`/`schema.json`.

## Shared field conventions that repeat across most components

These aren't one-off per-component config — they're conventions threaded through the registry, so learn them once:

**Catalog metadata** (asset bookkeeping, not business logic): `group_name` (str, often defaults to something like the vendor/integration name), `description` (str), `owners` (`List[str]`), `tags` (`Union[Dict[str,Any], List[str]]` — catalog tags, distinct from the manifest's own `tags`), `kinds` (`List[str]`, often auto-includes a vendor tag), `deps` (extra upstream asset deps beyond the component's own `upstream_asset_key`), `column_lineage`, `backfill_policy`.

**Partitions** (when a component supports partitioning — not universal): `partition_type` — one of `daily`/`weekly`/`monthly`/`hourly`/`static`/`multi`/`dynamic`/`cron`, or omitted for unpartitioned. `partition_cron_schedule` (required when `partition_type: cron` — an arbitrary cron expression, e.g. business-day-only cadences `TimeWindowPartitionsDefinition` can't express directly), `partition_cron_fmt` (strftime format for cron partition keys), `partition_start` (ISO date, required for time-based types), `partition_values` (comma-separated, for `static`/`multi`), `partition_dimensions` (multi-axis spec, overrides the flat fields), `partition_date_column` / `partition_static_column` (which upstream column filters rows to the current partition — only relevant to components that slice an upstream DataFrame/table per partition, like reverse-ETL sinks).

**Source/upstream wiring** (common on sink-shaped components): `upstream_asset_key` (str or list — the normal case, an upstream Dagster asset provides the data) **mutually exclusive with** `source` (inline config: `{kind: sql, resource_key/database_url_env_var, query}` or `{kind: csv, path, read_csv_kwargs}` or `{kind: inline, rows}` — for standalone/demo use without a real upstream asset).

**Freshness** (when present): policy fields describing how stale an asset is allowed to get before it's flagged — check the component's own `## Fields` for the exact field names, since Dagster's native `FreshnessPolicy` is itself partition-blind and some components compensate with their own config shape.

None of these are guaranteed on every component — a component only exposes the ones relevant to it (a pure-compute `transformation` component has no `source`/`upstream_asset_key` pair; most `sensor` components have no partition fields at all). Check `## Fields` before assuming one applies.

## Don't hallucinate — the concrete failure mode this prevents

A component's compact one-line description (what you'd see in `dagster-component search` output or a candidate catalog) is not enough to write YAML from. The single most common quality failure when generating Dagster YAML from memory is a plausible-but-wrong field name (`destination_table` when the real field is `target_table`, a snake_case field guessed in camelCase, a partition field name invented by analogy to a different component). Always close the loop with `dagster-component schema <id>` (or the README's `## Fields`) immediately before emitting `defs.yaml`/`example.yaml`, even for a component you've used before — schemas evolve, and `update` can rename or add required fields.
