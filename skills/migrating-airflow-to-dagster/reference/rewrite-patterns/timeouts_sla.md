# Timeouts and SLAs

`dagrun_timeout` / `execution_timeout`: the job tag `dagster/max_runtime` in seconds (`timeouts_sla.py`; what the converter does). It must be a RUN tag (`tags=` on `@dg.job` / `define_asset_job`): verified that a job tag lands on the run record, while the same key in `op_tags` stays an op tag and is not a run tag (do not use it for the run timeout). Dagster terminates a run only when run monitoring is enabled in the deployment (`run_monitoring` in dagster.yaml; not enabled or enforced in any test here): say so in the report. A timeout of one task inside a folded asset is a deadline in the code. `sla` / `sla_miss_callback`: `freshness_policy=dg.FreshnessPolicy.time_window(fail_window=...)` on the asset (exists on the installed
Dagster; verified to attach). An SLA measures time from the scheduled start, freshness measures the age of the data: not the same, and the callback itself (a notification) becomes an alert on the freshness state or a
run-failure sensor. Decision record (timeouts/sla): `preserved` or `not preserved: <why>`. Tested: the tag and the policy are present on the definitions; not tested: enforcement.
