"Re-computed" means the stored raw results of `stage1` were compared again with the changed harness (read only; `stage1` and its results were not modified): header parser fix, virtualenv baseline classification, and folded not-taken branches accepted as a representation difference. Nothing was re-run in Airflow or Dagster.

Lens: a `skipped` against `success` difference caused only by folding a not-taken branch into one asset is an **accepted representation difference** (Dagster has no state for code that is not run) when the side effects match and the decision record declares it. It is a **defect** when the state could have been expressed (the native optional-output form) or the effects differ.

## The four stage-1b DAGs that failed a gate, and the one `different` (re-read after the harness fixes)

Read from `stage1b-private/gates/`, `stage1b_gates.log` and the stored Airflow and rewrite results; the gates were then re-run with the fixed harness on COPIES of the projects (`stage1b` itself is untouched): **all 40 pass every gate**. None of the four was a defect in the rewrite.

| DAG | what the gate said | cause | classification and fix |
|---|---|---|---|
| `UI_features_toy` | `definitions_load`: module `rw_UI_features_toy.defs.UI_features_toy` not found | the worker named the file `_UI_features_toy.py` (a leading underscore, which `dg` accepts) and the harness computed the module name from the DAG id | **harness bug**: the gates now discover the package, the modules and the component folders under `src/<pkg>/defs/` and load the project through its own loader |
| `asset_with_extra_from_classic_operator` | same | same (`_asset_with_extra_from_classic_operator.py`) | **harness bug**, same fix |
| `load_file_to_S3` | `generated_tests`: 2 failed (`No module named rw_load_file_to_S3`) | `uv` and `create-dagster` lower-case the package (`rw_load_file_to_s3`); the harness used the DAG-id spelling, and the case-insensitive file system hid it from the `dg check defs` gate | **harness bug**: the folder on disk is the package |
| `my_dag_task_flow` | `generated_tests`: the materialize test failed (`Variable my_variable does not exist`) | the baseline sandbox exports `AIRFLOW_VAR_MY_VARIABLE`; the generated test did not | **harness bug**: the generated test now exports the spec's `AIRFLOW_VAR_*` and `AIRFLOW_CONN_*` exactly as the sandbox does |
| `fetch_extra_info` (`different`: tasks, failure) | `get_extra_triggering_run`: Airflow `failed`, rewrite `success` | the task is nondeterministic in Airflow itself: states across the four recorded runs were failed, success (kit run 2), failed, failed. The `VIRTUAL_ENV` warning of `dg` is also handled: the gates run `dg` from the project's own virtualenv with `VIRTUAL_ENV` unset. Two more things the stricter loader exposed while re-running all 40 projects: a DAG with an interval schedule (`tutorial`) was asserted to have NO schedule (the old test only saw one module, so it passed by accident): interval, asset and custom timetables are now `unchecked`, like the behaviour comparison; and a project that holds another DAG's schedule is judged by the schedules of its own job.
