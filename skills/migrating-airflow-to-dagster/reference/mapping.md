# Airflow to Dagster mapping

Class: MECH = translation is mechanical; JUDG = needs a judgment call or confirmation; REDESIGN = needs a design decision. "Verify" means check the current Dagster API with `dagster-expert` or `dg` before relying on the exact name.

## Choosing granularity

One asset per data product, with the steps that only help to produce it inside that asset: a data product is a task whose output is persisted (table, file, S3 key, dbt model) or whose returned value is consumed by more than the next step. Steps become plain Python inside the asset when no restart point is needed, and ops inside a graph-backed asset (`@dg.graph_asset` / `@dg.graph_multi_asset`) when a step has retries, a long runtime or an expensive external call; a failed op retries and restarts as an op, a plain-Python step restarts from the start of the asset. A chain of dataframe or SQL transformations is one registry pipeline component asset (`polars_pipeline`, `pandas_pipeline`, `warehouse_pipeline`, `pyspark_pipeline`) when the steps map to its ops. Notification, wait and cleanup tasks are not assets: they become sensors, hooks or run-status sensors, or fold into the producing asset. The converter applies part of this with `--granularity product` (`reference/conversion.md`, "Choosing granularity"); the rewrite route applies all of it (`reference/rewrite-route.md`).

## Structure

| Airflow | Dagster | Class | Notes |
|---|---|---|---|
| DAG | A job over the assets it produces, plus a schedule; or just assets with an automation condition | JUDG | Granularity is the decision: one asset per data product, not per task |
| Task producing data | Asset | MECH | The unit of migration |
| Task with no data output (notify, cleanup, wait) | Op in a job, a sensor, an alert, or folded into an asset | JUDG | |
| `EmptyOperator` / `DummyOperator` | Nothing; ordering is kept through asset deps. With an `outlets`/`inlets` declaration it is an asset (returns `None`) carrying the asset key | MECH | |
| TaskGroup | Asset `group_name` | MECH | |
| Task dependencies (`>>`) | Asset `deps` | MECH | Edges between non-data tasks collapse |
| Dataset / Asset outlets and inlets | Asset keys and deps | MECH | URIs become key paths; Airflow Asset URIs map naturally to Dagster keys |
| Several DAGs writing the same table | One producing asset; the others depend on it or are deferred | JUDG | Many definitions may depend on an asset; only one may produce it. See `reference/factories.md` rule 1 |
| Dataset-triggered schedule (`schedule=[...]`) | Asset deps with an automation condition such as `AutomationCondition.eager()` | JUDG | Verify; semantics differ from "all datasets updated since last run" |

|---|---|---|---|

| `@once` | Manual job, or a one-off | JUDG | |

| Custom timetable | Custom schedule function or sensor | REDESIGN | |
| `catchup=True` | Partitions (for example daily) plus a backfill | JUDG | Airflow's data interval versus Dagster's partition key: state the mapping in the equivalence row |
| `max_active_runs` | Run concurrency limits or tags | JUDG | Verify |
| `depends_on_past` | Partition dependencies or a custom condition | JUDG | |

## Behavior

| Airflow | Dagster | Class | Notes |
|---|---|---|---|
| `retries`, `retry_delay` | `RetryPolicy` | MECH | `retry_exponential_backoff` maps to a backoff setting; verify |
| `pool` | Dagster pool (`pool=` on the asset or op) | MECH | Limits are configured in Dagster (Dagster+ or the instance), not in code; list each pool and limit in the report |
| `execution_timeout` | Op/asset timeout or an inner timeout | JUDG | |
| XCom (`xcom_push/pull`, `.output`, and TaskFlow return values passed to another task, which are implicit XComs) | A return value is the asset's value (IO manager). A value pushed under a key is metadata on the asset's materialization; a keyed pull reads that metadata from the upstream asset's materialization in the same run (`convert_ir.py` does this) | JUDG | Decide per edge; do not assume an XCom backend exists. A pushed value must be JSON-serializable. Metadata is kept in the event log, so it suits small values |
| Variables | Environment variables or secrets | MECH | `dg plus create env` for Dagster+; never commit values |
| Connections (`conn_id`) | Resources configured from env vars | JUDG | |
| Jinja templates (`{{ ds }}`, `{{ data_interval_start }}`) | Partition key or run config | JUDG | |
| `on_failure_callback`, `on_success_callback`, `on_retry_callback` | The registry's `@on_hooks` decorator on the asset, with an adapter that rebuilds the callback's context dict (with `exception`). The failure callback runs after the last attempt only (the hooks fire on every attempt, so the adapter checks the retry count); `on_retry_callback` runs before each further attempt | MECH (asset form only) | Needs `dagster-community-components`. `ti.state` is set to `success`, `failed` or `up_for_retry` for the callback. Other hooks (`pre_execute`, `post_execute`, `@task.run_if`) and callbacks in the graph form are deferred |
| `on_execute_callback` (task or `default_args`) | Called at the start of every attempt, before the task's code, with the rebuilt context (`ti.state == 'running'`) | MECH (asset form only) | Airflow's transient states (`scheduled`, `queued`) are not reproduced; `on_skipped_callback` is not converted (a Dagster step has no skipped state of its own) |
| Notifier instances as callbacks (`on_failure_callback=[MyNotifier()]`, `BaseNotifier` subclass) | The class is copied (`BaseNotifier` is a plain runtime class whose `__call__` calls `notify(context)`) and an instance is rebuilt with the attributes it had (`__init__` is not run) | MECH | The notifier's `template_fields` are not rendered; an attribute that is not a plain value is dropped with a caveat |
| DAG `on_success_callback`, `on_failure_callback` | One `dg.run_status_sensor` per kind on the DAG's job, calling every function of that kind with a minimal context (`dag`, `dag_run` with `state`, `run_id`, `logical_date`, `ds`, `ts`, `reason`, `exception` = the run failure message) | MECH | Needs the sensor daemon; runs after the run ends. No task instance in the context. `sla_miss_callback` and the DAG `sla` have no run-level equivalent (use freshness checks or an alert policy): reported as degraded |
| SLAs / `sla` | Freshness policy or alert | JUDG | |
| `default_args` | Applied per asset (retries, owners) | MECH | |

## Generated pipelines

| Source | Handling |
|---|---|
| dag-factory YAML | The scanner reads the YAML; migrate the generated DAGs' tasks as above. Consider a Dagster component when the same shape repeats many times. |
| Cosmos | See the Cosmos rows above and `reference/conversion.md`. `ProfileConfig` becomes an `env_var()` based `profiles.yml` (names only); a profiles file is never copied. |
| Jinja-heavy or programmatically generated DAGs | The static scanner may miss them; run the project's DAG parse once (`airflow dags list` in a sandbox) and compare counts with the manifest. |

## Scanner accuracy and limits

Measured by comparing the scan with Airflow's own parse (DagBag) of five public repos. "Exact" is task ids equal to Airflow's; "flagged" is tasks in DAGs where the scan holds a `dynamic_id`, `in_loop` or `mapped` unit because the real ids exist only at parse time; "unaccounted" is neither.

| Repo (Airflow used for the parse) | DAGs found / Airflow produced | Task ids exact | Flagged | Unaccounted |
|---|---|---|---|---|
| apache/airflow example DAGs, main (3.4.0) | 118 / 118 | 75% of 427 | 25% | 0 |
| astronomer/2-10-example-dags (2.10.5) | 25 / 25 | 100% of 55 | 0 | 0 |
| astronomer/2-9-example-dags (2.10.5) | 18 / 18 | 100% of 44 | 0 | 0 |

Re-run the comparison on your own repo rather than assuming these numbers carry over.

What the static scan models: DAGs by `with DAG`, `DAG(...)`, `@dag` and `@asset`; tasks at their call sites with group prefixes and Airflow's duplicate-call suffixes; `.override`, `.partial`, `.expand`, `.loop`; `>>`, `<<`, `chain`, `set_downstream`, TaskFlow argument passing; dag-factory YAML.

What it does not: DAGs or tasks produced by factories in other files, loops with unknowable counts, constructs added after it was written (it flags `.loop` groups but cannot name synthetic tasks such as `__loop_gate`), or code behind conditional imports. It reports unparsable files as `unparsed`, keeps computed task ids as `dynamic_id` and loop-created tasks as `in_loop` (one source task may be many), and `reconcile.py` closes the remaining gap against a real Airflow parse. When the manifest's DAG count disagrees with the instance's, trust the instance.

## Alignment with the verified pattern library

The converter and the rewrite route share one set of verified Dagster patterns (`reference/rewrite-patterns/`, statuses in `index.json`, tested on the installed Dagster). `scripts/pattern_emit.py` reads that index at conversion time and embeds the library's own code in the generated runtime (today: `previous_run_failed` for `depends_on_past`); `scripts/tests/test_converter_patterns.py` fails when the converter's form or tables diverge from the library's and executes converter output for each pattern. Per pattern:

| Pattern | Converter | Why |
|---|---|---|
| depends_on_past | **adopted** (asset form): the library's step-event guard, embedded from the library source; degraded caveat states fail-instead-of-wait | VERIFIED; before, nothing was enforced. Graph and partitioned forms keep the old caveat (step keys differ; the partitioned guard is a different, newer form) |
| venv operators | **adopted in part**: a missing interpreter fails loudly, never the current one | Pipes not used: the converter returns the callable's value (pickled), Pipes reports metadata |
| templating | **fixed**: a time-partitioned run with no schedule tags takes `ds` and the interval from the partition window (the library's `partition_key`/`partition_time_window`), not from the clock | disagreement found, see below |
| branch / short circuit | left as is: one graph asset with a gate per op | the library's optional-output form is verified for a single `graph_asset`/`multi_asset`, not for this converter's `graph_multi_asset` with one output per task; it expresses only all_success joins (the converter also runs `none_failed*`, `one_success`, `all_done`, setup/teardown), and an unyielded output leaves no materialization where the converter records `airflow/state: skipped` (the evaluation harness reads that; a missing materialization reads as `not_run`) |
| mapped tasks, empty expansion | left as is: DynamicOut + `.map` + `.collect` already; an empty expansion skips the mapped step and what is below, with the state recorded (Airflow's behaviour). `DynamicOut(is_required=False)` gives the same skip in a single `graph_asset`; here it would drop the materialization and the trigger-rule gates downstream | executed test |
| trigger rules | left as is: the converter's table covers every rule in the run; the library's hooks/sensor forms cover `all_done` and a post-run handler only | PARTIAL claims in the library |
| sensors | left as is: poll in the step (the library's fallback form, same-run), `poke` semantics with one more poke at the timeout than `poll_until` | same outcomes asserted; a Dagster sensor changes the pipeline shape |
| TriggerDagRun / ExternalTaskSensor | TriggerDagRun is a real in-run launch with `wait_for_completion` (not a stub); ExternalTaskSensor and asset schedules use `AutomationCondition.eager()` as the library | the library's `run_status_sensor` form is PARTIAL and loses the wait |
