# The rewrite route: spec, prompt, gates

Inside tier 3 (Dagster owns the code) there are two routes for how the code gets written. **Convert**: the deterministic converter, a near like-for-like conversion of what Airflow built. **Rewrite**: build a thorough, deterministic understanding of one DAG, hand it to Claude as a generated prompt, and have Claude write the Dagster code from scratch with `dagster-expert` and `dagster-community-components`, accepted only through gates. The rewrite is expected to be more idiomatic (one asset per data product, glue folded away, registry components) and to cover operators the converter stubs. This page gives the evidence rather than the claim.

## The three scripts

| Script | What it does |
|---|---|
| `scripts/dag_spec.py ir.json [--report] [--manifest] [--parity]` | `rewrite/<dag>.spec.{md,json}`, per DAG, deterministic. Facts only: tasks, operator types and resolved arguments, the source of every callable and of function-valued arguments (a sensor's `response_check`), dependencies, value (XCom) flow, assets in and out, schedule, timezone, catchup, retries, pools, timeouts, callbacks, SLAs, connection and Variable **names**, trigger rules, branching and mapping, the dbt project and selection for Cosmos. Purpose is stated only as what the facts support and marked *inferred*. Also: what the converter did and where it stubbed or degraded (as a reference), the Airflow parity baseline when given, and an explicit list of behaviours that must be preserved against differences that are acceptable. No secret value: credential-like arguments and string literals assigned to credential-like names are redacted. |
| `scripts/rewrite_prompt.py <spec.json> [--converter-module] [--converter-project DIR] [--spec-ref NAME]` | `rewrite/<dag>.prompt.md`: a self-contained prompt. It tells Claude to load `dagster-expert` and `dagster-community-components` (by name, and the repository path `skills/dagster-community-components/SKILL.md` for agents that load skills from files), follow the per-stage search, verify, schema, add and wire, validate recipe of that skill's `reference/demo-workflow.md` with its real commands (`dagster-component search "<term>" --json`, `info`, `schema <id> --format json`, `add`, `list --available`; `dg list components --json`; `dg check defs`), record the id, schema fields and validation tier of every component chosen (an unvalidated tier carries a caveat), embeds the spec, states the target idioms (one asset per data product, ops only where restart points matter, one pipeline component for dataframe chains, glue as sensors, hooks and run-status sensors), lists the acceptance gates, and says the converter's output is a draft for reference and the fallback. |
| `scripts/accept_rewrite.py --spec --project [--module] [--defs-dir] [--parity] [--baseline] [--source] [--manifest]` | The gates, and the manifest record of which route produced each unit. `--module` and `--defs-dir` are optional hints: the package, modules and component folders are discovered under `src/<pkg>/defs/`. |

## The gates

| Gate | Passes when |
|---|---|
| `definitions_load` | `dg check defs` passes in the project (the project's own `dg` is used and `VIRTUAL_ENV` is unset for the run, so an outer virtualenv does not make it warn or fail; when `dg` is not installed, the project's definitions loader is run instead and the gate says so) |
| `generated_tests` | a behavioural contract written to `tests/test_<dag>_rewrite.py` passes (it loads the project through its own definitions loader, never through module-level variables, and exports the spec's `AIRFLOW_VAR_*` and `AIRFLOW_CONN_*` as the behaviour sandbox does): the definitions load and hold assets, a job named after the DAG exists, the schedule's cron and timezone equal Airflow's, and for a DAG with no external system the whole DAG materializes and every asset check passes. The converter's key-for-key tests do not apply: a rewrite picks its own keys |
| `asset_checks_present` | at least one structural check when the converter derived any from the source (a rewrite folds steps, so it has fewer places to check) |
| `parity` | with an Airflow baseline: the same overall outcome, and the same value as Airflow for every task the header says is `replaced by` an asset. Without one: `not run (no baseline)`, recorded as such |
| `no_secret_values` | no credential-looking literal in any module or `defs.yaml` under `defs/` (the gate never echoes the literal) |
| `no_invented_apis` | every import and every component `type:` resolves to something that exists |
| `tasks_accounted_for` | the header (the docstring of any module under `defs/`, or the `#` comment block of a `defs.yaml`) names every Airflow task and says what happened to it (replaced, folded, dropped, merged), and the asset KEY a task is `replaced by`, `folded into` or `merged into` exists in the loaded definitions (found as `dg list defs` / the `Definitions` object lists it) |

### Two project shapes, accepted on equal terms

A rewrite is a `create-dagster` project, and the gates look at it through its own definitions loader (`src/<pkg>/definitions.py`, `dg check defs`, the loaded `Definitions`), so both shapes pass identically:

- **module style**: `defs/<name>.py` with `@dg.asset` functions (any file name; a leading underscore or a lower-cased package name does not matter);
- **component style**: a folder per registry component under `defs/<id>/` with a `defs.yaml` (`dagster-component add <id>` writes the source under `src/<pkg>/components/<id>/` and the `defs.yaml`), plus a small `.py` next to it for the job and the schedule. The header may be the `#` comment block of the `defs.yaml`.

Assets, the job named after the DAG, the schedule (cron and timezone) and the asset checks are found by key and name in the loaded definitions, not by variable name. The prompt tells workers component projects are fine and preferred when a registry component fits (registry first). `eval_gates.py` records per DAG which registry components the project uses (read from the `defs.yaml` `type:` entries and the `.dg-community.json` marker) and whether the worker's report says searches were run, and `eval_report.py` reports both, so "registry first" is measurable. `scripts/tests/test_rewrite_components.py` runs every gate on a real component project (`shell_command_asset`, validation tier `live`, installed with `dagster-component add` from the live registry into a `create-dagster` project and vendored under `scripts/tests/fixtures_component_project/`).

With `--manifest`, each unit of the DAG gets `route: rewrite` and the gate results: all passed, the unit is advanced with the evidence; otherwise it stays or becomes `deferred` with the failures, and the converter's output remains the fallback. A unit the converter already completed keeps `route: converter` and gets a `rewrite_attempt` note. The converter's units carry `route: converter`. `plan.py` has a Route column, and the cutover checklist shows which route produced the code and the gate results.

## Worked examples

`examples/rewrite/` has two real DAGs: `simple_sequential_pipeline` (the converter handles it) and `partner_ingest` (the converter stubs two tasks). I wrote both rewrites by following the generated prompts. Both pass all seven gates; the README there compares them with the converter's output (one asset against three, 52 lines against 100 plus a shared 1,561-line runtime; two assets that run against five assets of which two are loud stubs) and lists what the spec missed and what was fixed in the generators.

## Measured: both routes on a sample (8 DAGs, not a benchmark)

**Read this section as a first look, not a measurement.** The agent that designed the prompts also wrote these rewrites (they are not cold), the sample is 8 DAGs, and the table mixes "loads and has the right shape" with "behaves like Airflow" (parity was run for only some DAGs, and compared values and the outcome, not files, requests or mail). The behaviour measurement against real Airflow, by workers who did not design the prompts, on a large sample, has its own harness and run book: [rewrite-route-evaluation-runbook.md](rewrite-route-evaluation-runbook.md), and its generated report [rewrite-route-evaluation.md](rewrite-route-evaluation.md) (empty of numbers until that run has been done).

**Sample size, plainly.** The target was at least 10 DAGs the converter defers or stubs plus 10 it converts cleanly. I ran **4 + 4 = 8**: the two worked examples above and six more from public Astronomer example repositories (`2-5` to `2-10-example-dags`, `airflow-example-dags`, `astro-example-dags`: 114 DAG files, 81 DAGs extracted with Airflow 2.10.5, of which the converter handles 61 cleanly, stubs part of 19 and defers 1). Fewer than asked because every rewrite is performed by me, one at a time, in this session; I counted the rewrites I performed (**8**) and extrapolated nothing. These are teaching DAGs (macros, datasets, pools, Jinja), chosen small and diverse, not a typical estate, so the numbers show what the routes do on these DAGs and nothing about yours. Artefacts: `examples/rewrite/sample/` (IR, specs, generated prompts, gate results, the converter's modules, the rewrites in a `dg check defs` project, Airflow's results).

| DAG | Converter: result | Converter: gates | Rewrite: structure | Rewrite: gates |
|---|---|---|---|---|
| `simple_sequential_pipeline` (clean) | 3 assets, 2 structural checks | its generated tests pass; Airflow parity not run for it | 1 asset, 1 check, 52 lines | 7 of 7 |
| `toy_taskflow_bash` (clean) | 2 assets, 1 check | tests pass (shell materialize needs `CONVERTED_TESTS_RUN_SHELL=1`); parity: identical outcome | 1 asset, 1 check, 42 lines | 7 of 7 (parity: same value as Airflow) |
| `literal_wrapper_example` (clean) | 2 assets | tests pass; parity: identical outcome (**Airflow's own run fails** on Airflow 2.10.5: `LiteralValue` has no `endswith`; the converter's output also fails) | 1 asset, 1 check, 38 lines | **6 of 7: parity fails**: Airflow failed, the rewrite succeeds |
| `pool_example` (clean) | a graph asset with a mapped op and the pool (2 assets in the report) | tests pass; parity: identical outcome | 1 graph asset (3 ops, pool on the mapped op), 1 check, 53 lines | 7 of 7 (parity: outcome only) |
| `partner_ingest` (2 stubs) | 5 assets, **2 loud stubs** | shape tests pass; units deferred; the DAG fails at the first stub | 2 assets, 1 check, 88 lines; runs against a local stand-in | 7 of 7 (no Airflow baseline) |
| `babel_format` (1 stub: `macros.ds_format_locale`) | 1 asset, **stub** | shape tests pass; materialize skipped (stub) | 1 asset, 1 check, 30 lines | 7 of 7 (no baseline: not run) |
| `json_yaml_macros_toy` (2 stubs: `macros.json`, `macros.yaml`) | 2 assets, **2 stubs** | shape tests pass; materialize skipped | 1 asset, 1 check, 33 lines | 7 of 7 (no baseline) |
| `basic_dataset_schedule_upstream_2` (1 stub: a name from an Airflow import) | 1 asset, **stub** | shape tests pass; materialize skipped | 1 asset (the Dataset's key), 0 checks (the source has nothing checkable), 17 lines | 7 of 7 (no baseline) |

**Pass rates on this sample.** Converter: the 4 clean DAGs pass their generated tests (4 of 4) and, where parity was run, match Airflow (3 of 3); the 4 stubbed DAGs are translated only in shape (0 of 4 fully translated; every stubbed task fails when run, by design). Rewrite: 7 of 8 pass all seven gates; the eighth (`literal_wrapper_example`) fails the parity gate because the Airflow baseline itself fails, which the gate cannot tell apart from a behavioural difference (the converter's output reproduces that failure and so "matches"; whether a rewrite should is a decision for a person). Operators covered: the converter's stubs were a Jinja macro (`ds_format_locale`, `json`, `yaml`) three times, an Airflow import once and a function-valued sensor argument plus an Airflow connection read once; the rewrites replaced each with the library the macro stands for or plain Python. The converter route's ceiling on this sample is what it can translate mechanically; the rewrite route had no such ceiling but its evidence is thinner (no Airflow baseline for the DAGs that needed it most: they call external systems or use macros that were not eligible).

**Effort.** 8 rewrites performed, one writing pass each plus the generator fixes below, against under a second for the converter. Not extrapolated to 100 DAGs.

**What failed, why, and the generator fixes (made for the class, not per DAG).** No rewrite failed a gate through a defect of its own. The sample exposed gaps in what the spec and gates knew, each fixed in the generators:

| Pattern | What was missing | Fix |
|---|---|---|
| a function passed as an argument (a sensor's `response_check`) | its logic was not in the spec | the IR records the user's function arguments' source; the spec prints it |
| a connection read inside a callable (`BaseHook.get_connection("x")`) | not listed as a connection | the spec finds `get_connection("...")` calls (names only) |
| DAG `params` (`context["params"]["num_guests"]`) | not shown in the spec's Markdown | a "DAG parameters" section |
| `user_defined_macros` (`{{ my_json }}`) | not in the IR or the spec: my first `json_yaml_macros_toy` rewrite had to invent example values | the IR records them (values, and the names of function macros); the spec prints them; the rewrite now uses the real values |
| a value reference `{"xcom_from": ..., "key": "return_value"}` | the `key` was masked as if it were a credential | value references are never masked |
| Airflow internals in a mapped task's arguments (`deps`, `expand_input`) | noise in the spec | dropped |
| a pool | its slot count is not in the IR (it lives in Airflow's metadata database) | the spec says so and the rewrite's header says how to set the limit |
| gate: structural-check count | demanded as many as the task-per-asset converter derived | at least one when the converter derived any |
| gate: parity of folded tasks | compared a folded task's value with the merged asset | only tasks the header says are `replaced by` an asset are compared (a task `merged into` or `folded into` another is not) |
| gate: secret literal | the failure message echoed the literal | it names the variable and the line only |

Remaining pattern, not fixed: the parity gate cannot distinguish a baseline that fails for an environmental reason from a behavioural difference (`literal_wrapper_example`); it reports the difference and leaves the decision to a person.

## When to use it

For a DAG the converter deferred or stubbed, a redesign-heavy DAG, the plan's last wave, and the pilot DAGs where idiomatic output matters while the mapping is being learned. Keep the converter for the mechanical bulk. **Cost:** the rewrite spends model effort on every DAG (the prompt is 14 to 16 KB for these two, the model reads it, searches the registry and writes the file, and a failed gate means another pass); the converter takes under a second. The plan's effort figures do not include it.


## Changes after the cold-writer measurement

The measurement (`reference/rewrite-route-evaluation.md`, 40 DAGs) found the route 70% equivalent in either form and 12 DAGs `different`, mostly branching. The triage of those 12 is `reference/rewrite-route-triage.md`. In response: the prompt injects a pattern library (`reference/rewrite-patterns/`, native Dagster forms first, plain Python as the declared fallback, every code file executed by a test, `index.json` with VERIFIED / PARTIAL / FAILED claims); the "acceptable differences" text no longer lets a task's `skipped` state be dropped silently; two gates were added (`task_states`, `decision_record`); a worker can run `tools/compare_behavior.py` in its kit and iterate on behaviour differences against a baked Airflow baseline; `eval_report.py` counts `not preserved` declarations and fallbacks. What these changes do to the pass rate is NOT measured yet: `stage1b` (same DAGs, new kit) is the run that measures it.

After the first workers ran (stage1b), three harness and library corrections were made: (1) joins below a skipped upstream were checked by shape (`rewrite-patterns/branching.md`: a separate top-level join is skipped if any upstream is skipped; a join `graph_asset` with pass-through ops and a fan-in list, a marker output, or the sentinel form run it); (2) the generated pytest of the `generated_tests` gate now asserts the SAME failure when the Airflow baseline shows the DAG's own run failing (by design, or a virtualenv / external-interpreter task that cannot build in the sandbox), and keeps expecting success without a baseline or for any other environmental baseline failure; (3) a branch or short-circuit whose callable reads the clock or a random number is detected (`parity/behavior_compare.py: nondeterministic_decisions`), the task states below it are reported as `nondeterministic: not compared` while outcome and failure behaviour are still compared, and `eval_report.py` lists those DAGs. On the 40 stage1 DAGs the detection triggers on `example_branch_dop_operator_v3` (the minute), `example_branch_operator` (both repositories) and `new_branching_decorators_example` (`random.choice`).

## The prompt after stage 2a: resource-first, a registry-search checklist, an optional converter starting point

The prompt changed after the stage 2a measurement (the stage 2a rewrite numbers belong to the previous prompt; see `reference/rewrite-route-evaluation.md`). What changed, all offline and not yet measured on workers:

- **Resource-first rule** (every prompt) and a **compact registry-resource table for only the service-operator families the spec uses** (`scripts/rewrite_resources.py`, from `reference/registry-resources-0.10.194.md`): a service-calling operator is a registry RESOURCE configured once and called inside the asset or op, not an asset of its own and not a hand-rolled client. The table carries each family's gap and the warnings (Fivetran: do not map yet; dbt Cloud: the resource disables the job schedule on trigger). The worker's installed templates may be older than 0.10.194: it runs `dagster-component info <id>` first and falls back to plain Python, saying so.
- **Registry-search lines**: one line per stage (`- <stage>: searched "<terms>": found <id> | not found; used | not used: <reason>`) in a separate paragraph after the decision record, with candidate ids seen in earlier registry searches. `accept_rewrite.py` is unchanged: its decision-record gate reads only the `Decision record:` paragraph, so these lines are not checked yet.
- **Smaller by what the DAG shows**: the long native-forms paragraph and the state table are cut to the constructs the spec shows; the plain-Python branching fallback code is no longer pasted (its text stays); the empty converter stub in the spec is dropped; the gate list and the skills section are shorter. A smaller prompt is NOT shown to give equal accuracy: that needs a new worker measurement.
- **`--converter-project DIR`** (default off): the worker starts from the converter's emitted project and the report's stubs, degraded sections and notes are its TODO list. `--spec-ref NAME` points at the spec file instead of pasting it.
