# ADF to Dagster mapping: what is translated, what is a stub, what is verified

"Tested" means covered by this repo's tests and a four-gate run on the synthetic factory (`tests/fixtures/synthetic`). Nothing has been compared with a live ADF run.

## Tier 1: observe and orchestrate with the registry component

```yaml
type: dagster_community_components.AzureDataFactoryComponent
attributes:
  workspace:
    subscription_id: "{{ env.AZURE_SUBSCRIPTION_ID }}"
    resource_group_name: my-resource-group
    factory_name: my-data-factory
    tenant_id_env_var: AZURE_TENANT_ID
    client_id_env_var: AZURE_CLIENT_ID
    client_secret_env_var: AZURE_CLIENT_SECRET
  import_pipelines: true
  import_triggers: true
  polling_sensor: true
  group_name: adf_prod
```

Omit the three `*_env_var` fields to use managed identity or the Azure CLI. From the component's own example; not run here.

## Copy

| Pair | Output | Notes |
|---|---|---|
| file to file, same format and same format settings (any of Binary, DelimitedText, Json, Parquet, Avro, Orc, Xml) over Blob, ADLS Gen2, S3 and a file server | byte copy through fsspec (`abfs://`, `s3://`, local path); `recursive`, `wildcardFileName`, `wildcardFolderPath`, `copyBehavior` PreserveHierarchy / FlattenHierarchy | checksums, file-level logging and DIU settings are not reproduced |
| file to file, between delimited text, JSON and Parquet (and from Excel), or delimited text with different delimiter, quote, header, encoding or compression | read and written through pandas and pyarrow: each input file becomes one output file named like it with the new extension, or all inputs merge into the sink's file name when it has one. Delimited text and Excel are read as text (no schema is applied); nested JSON is flattened with dots; compression none, gzip and bzip2 (delimited text, JSON) and snappy and gzip (Parquet) | other codecs, Avro, Orc and Xml reformats, an Excel `range`, and `skipLineCount` are stubs; the column types ADF would apply from a mapped schema are not |
| REST to a JSON or delimited text file | the response body is written as received. With `paginationRules`, a `collectionReference`, path mappings or a `requestInterval`, pages are fetched by the REST connector's documented pagination rules (`AbsoluteUrl`, `QueryParameters.x`, `Headers.x` taken from a `$` JSONPath or a response header; `RANGE:start:end:step` variables in the url, query parameters and headers, with an empty end running until an `EndCondition:` of `Empty`, `NonExist`, `Exist` or `Const:x`; `MaxRequestNumber`; HTTP 204 and a null rule value end the loop; with no rule, RFC 5988 `Link` headers are followed) and the rows are written one JSON object per line, or as delimited text. Path mappings follow the schema-mapping page: a path starting with `$` reads the document root, any other path the current element of the `collectionReference` array (one row per element, root values repeated; an empty array skips the record). The default pause between pages is the documented 1 second; `httpRequestTimeout` defaults to 100 seconds. A base url not in the export is read from `ADF_REST_URL_<name>` | anonymous auth only (other auth is a stub, and when the service is not in the export none is sent: reported); pagination keys outside the documented vocabulary are stubs; ADF re-serialises REST results, so layout can differ without a mapping (reported) |
| delimited text, Parquet, JSON or Excel files into a SQL table | batched `INSERT` over SQLAlchemy, `preCopyScript` run first in the same transaction, named column mappings from a `TabularTranslator`. `writeBehavior: upsert` (with literal `upsertSettings.keys`) updates the row with the same key values and inserts the rest, one row at a time; `tableOption: autoCreate` creates a missing table from the values copied. Delimited text needs a header row | stored-procedure sinks are stubs. Delimited text goes in as text and empty fields as NULL; an auto-created table gets text columns for delimited text; Parquet, JSON and Excel values are inserted as read and an existing table's column types apply |
| SQL table or query to delimited text, JSON or Parquet | query result written as CSV (the sink dataset's delimiter, quote, header), JSON (one object per line, or an array when the sink says `arrayOfObjects`) or Parquet; a sink with no file name gets `data_<guid>.txt` / `.json` / `.parquet` (ADF also generates a name, the pattern may differ) | stored-procedure sources are translated for the SQL Server family only (`EXEC name @p = :p`, parameters bound); `isolationLevel` is applied to the read connection; `partitionOption` is reported, not applied |
| SQL to SQL (the SQL Server family, plus Postgres, MySQL, Oracle and Snowflake through a SQLAlchemy URL and the driver you install) | streamed in chunks into an existing table with a `preCopyScript` and column mappings. At the top level of a splittable pipeline with literal tables or query it is a `sql_to_database_asset` asset instead (see Splitting; `writeBehavior: upsert` with literal `upsertSettings.keys` becomes `if_exists: upsert`; a `preCopyScript` or column mappings keep it inline); inside a loop or condition, or with expressions, it runs inline | the Snowflake, MySQL and Oracle type names come from ADF's connector list, not an export (AzurePostgreSql and Oracle appear in the public repos) |

A linked service that is missing from the export is not a stub when the dataset or activity already says what kind of store it is: the converter reads the credentials from `ADF_FS_<name>` (files), `ADF_CONN_<name>` (SQL) or `ADF_REST_URL_<name>` (REST) and says so in the report.

File sources also take the connector pages' filters: `modifiedDatetimeStart` (inclusive) and `modifiedDatetimeEnd` (exclusive), `fileListPath`, `prefix`, `enablePartitionDiscovery` (key=value folders become string columns), `MergeFiles` for same-format copies (the files' bytes joined in name order) and `deleteFilesAfterCompletion` for binary copies only (each file removed after it was copied).

Not translated and therefore stubs: Dynamics, Salesforce, Jira, SAP, Office 365 and other application connectors; Lakehouse, Warehouse and Snowflake sinks with Fabric's inline `datasetSettings` format; Azure File Storage locations; a stored-procedure sink; REST pagination outside the documented vocabulary; legacy v1 sources with no datasets. Settings such as `enableSkipIncompatibleRow` and `validateDataConsistency` are reported as not enforced.

Storage credentials come from the environment: `ADF_FS_<LINKED_SERVICE>` is a JSON object of fsspec storage options (for blob and ADLS `account_name` plus a key, SAS token or service principal; for S3 `key` and `secret`). Nothing is copied from ADF. A file server linked service is a local path on the machine running Dagster. The tests cover the file server, REST, and SQL pairs with real I/O (local files, sqlite, a local HTTP server); the blob, ADLS and S3 paths are generated and checked for text only, never run against those services. Parquet, JSON, Excel and CSV conversions, SQL to Parquet, Parquet into SQL and SQL to SQL are tested with real files and sqlite.

## Splitting a pipeline into assets

A pipeline is one run with shared state; a registry component is its own asset. A pipeline with top-level SSIS, Synapse notebook, Synapse Spark job, literal Fabric notebook or SQL-to-SQL Copy activities is cut into Python segments (`<pipeline>` or `<pipeline>__part1`, `__part2`...) and component assets joined by asset dependencies taken from ADF's `dependsOn`, so each package, notebook, job and copy is its own node in lineage. The components load offline with no subclass: the YAML uses the registry components directly (`SsisWorkspaceComponent`, `AzureSynapseComponent`, `FabricWorkspaceComponent`, `SQLToDatabaseAssetComponent`), declares the packages, notebooks and jobs from the ADF activities (`packages:`, `notebooks:`, `spark_jobs:`), and sets `dry_run: "{{ env.ADF_DRY_RUN == '1' }}"`, so with `ADF_DRY_RUN=1` nothing connects. A real run uses the registry component's own code. Only `warehouse_pipeline` (a data flow translated to SQL) goes through a small generated subclass, because it has no `dry_run`.

The split only happens when every condition holds; otherwise the pipeline stays one asset and each component-backed activity is a loud stub that says which condition failed:

- the activity is at the top level of the pipeline (not inside a ForEach, If, Switch or Until);
- its values are literals (an expression cannot go into a component's configuration);
- every top-level dependency is `Succeeded` (a `Failed`, `Skipped` or `Completed` edge cannot cross an asset boundary);
- no activity reads another activity's output, or a variable set elsewhere, across a cut (separate assets do not share run state);
- the pipeline is not run by another pipeline's ExecutePipeline (which calls it inline) and is not partitioned by a tumbling window trigger.

A Fabric notebook that cannot be split off (expressions, or any of the conditions above) is not a stub: it falls back to the inline client call. A split pipeline's run is a run of all its assets: a schedule targets all of them, and its parameters are set per Python segment (each takes only the parameters it uses).

## Mapping Data Flows

`ExecuteDataFlow` runs the flow's script (`typeProperties.script` or `scriptLines`) in the generated project's Python process: `dflow.py` is copied next to `runtime.py`, every stream is a list of dicts, and each transformation is applied in turn. It is exact rather than fast (whole tables and files are held in memory) and nothing runs on Spark.

| Part | Translated |
|---|---|
| Transformations | source, sink, select (`mapColumn` renames and drops), filter, derive, sort (`asc`/`desc` with the null-ordering flag, `caseInsensitive`), aggregate (`groupBy`), join (inner, left, right, outer and cross, any condition; `Stream@column` names a side), union (by name or by position), exists (and `negate`), lookup (`multiple`, `pickup` any/first/last with sort conditions, `isMatch()`), conditional split (`disjoint` and a default stream), surrogate key (`keyGenerate`, `startAt`), rank (standard and dense), alter row (insert, update, delete and upsert policies, on SQL sinks), window (`over`, sort conditions, aggregates over the whole partition, `rank`, `denseRank`, `rowNumber`, `lag`, `lead`, `nTile`, `cumeDist`), pivot (`groupBy`, `pivotBy` with or without listed values, `columnNaming` with `$N` and `$V`), unpivot (`ungroupBy`, `pivotValues`, `ignoreNullPivots`) and flatten (`foldDown` with `unroll` and an optional root, over nested JSON) |
| Not translated (the whole flow is a stub naming them) | parse, call, assert, cached sinks and lookups, bounded window frames (`startRowOffset`), rule-based flatten mappings, a pivot with no `columnNaming`, column patterns (`each(match(...))`, `$$`), `byName()`, complex or nested columns, `#lookup`, `#outputs`, fuzzy joins, `===` |
| Expressions | the data flow expression language: operators with null propagation, `iif`/`case`, string, math, conversion, date and aggregate functions. Every documented example of an implemented function is a test (101 run); a function with a format or locale argument, a date pattern beyond `y M d H m s`, or a time zone is refused at conversion time, never guessed. `<=>` and `equalsIgnoreCase` ignore case |
| Sources | datasets or inline datasets: SQL table or query (and a stored procedure with no inputs), delimited text, Parquet and JSON over blob, ADLS Gen2, S3 or a file server, Excel (sheet, no range). Delimited text is read as text and cast to the types the script declares; a file without a header row takes its column names from the projection by position. `wildcardPaths`, file lists and partition options are stubs |
| Sinks | SQL tables (`truncate`, `preSQLs`, key columns for updates, deletes and upserts; only columns the table has are written) and delimited text, Parquet or JSON files (`partitionFileNames` with one name, else a Spark-style `part-00000-<guid>-c000` file; `truncate` clears the folder first). Other stores (Synapse lake databases, Cosmos DB, Dynamics, cache) are stubs |
| Parameters | `parameters{...}` defaults, overridden by the activity's values (an ADF expression or a data flow expression) |

Derived columns see the incoming row, not the columns derived earlier in the same transformation (the page does not say; unverified). The activity's output carries `runStatus.metrics.<sink>.rowsWritten`; compute, staging and tracing settings are reported as not applied.

A flow whose sources and sinks are SQL tables or queries in **one** database, whose sinks all `truncate`, and whose columns are all declared in the sources' `output(...)`, is first tried as the registry's `warehouse_pipeline` component (`docs/DATAFLOW.md`): each transformation is a SQL step, each sink a table rebuilt with `CREATE OR REPLACE` (grants, indexes and columns the flow never wrote do not survive), one Dagster asset per sink, with the pipeline's other activities as assets around it. Literal parameters are put into the SQL; a parameter from a pipeline expression keeps the flow inline. The SQL is checked against the inline executor on the same rows (every transformation above except flatten and alter row), and once on DuckDB through the component itself; not against ADF or SQL Server. None of the 76 public flows with a script qualifies (they are mostly file flows), so this path is exercised by tests, not by the corpus.

## Dependencies and the pipeline's outcome

An activity runs only if each dependency finished with one of the listed conditions (`Completed` means Succeeded or Failed); otherwise it is Skipped, and a Skipped activity satisfies only a `Skipped` condition (Microsoft's activity-dependency description).

Whether a scope (a pipeline, or the body of a ForEach, If, Switch or Until) failed follows Microsoft's documented rule ("How pipeline failures are determined", error-handling tutorial): look at every leaf activity (one nothing depends on); a leaf that was skipped is judged by its parent instead, and so on up; the scope succeeds only if every judged node succeeded. So an activity with only an `Upon Failure` handler is handled (try-catch: the pipeline succeeds), one with both `Upon Failure` and `Upon Success` branches fails the pipeline when it fails (the skipped success leaf points back at the failed parent), and adding a dummy `Upon Skip` after the success branch makes it succeed again. All of that is a test (`test_pipeline_outcome_follows_the_documented_leaf_rule`, eight cases from the summary table).

Independent branches run one after another, not in parallel.

## Expressions

Any string that starts with `@` (not `@@`) or holds `@{...}` is an expression, with or without the `{"type": "Expression"}` wrapper; `@@` is a literal `@`. Parameter, variable and activity names are matched ignoring case, as ADF does. Supported (anything else makes the activity a stub, never a guess): `pipeline().parameters.x`, `pipeline().globalParameters.x`, `pipeline().Pipeline / RunId / DataFactory / TriggerType / TriggerName / TriggerTime`, `variables('v')`, `activity('A').output / error / status / statusCode` with property and index access (`?.` for optional), `item()`, `trigger().outputs.windowStartTime / windowEndTime`, `trigger().scheduledTime / startTime`, `@{...}` interpolation, `@@`, and these functions: concat, equals, not, and, or, if, string, int, float, bool, contains, replace, split, join, length, empty, first, last, add, sub, mul, div, mod, greater, greaterOrEquals, less, lessOrEquals, formatDateTime, utcnow, addDays/Hours/Minutes/Seconds, addToTime, subtractFromTime, startOfDay/Hour/Month, dayOfMonth/Week/Year, startsWith, endsWith, toLower, toUpper, trim, substring, indexOf, coalesce, json, createArray, array, union, take, skip, base64, base64ToString, uriComponent, guid, min, max, range, binary.

`formatDateTime` takes .NET custom formats (yyyy, MM, dd, HH, mm, ss, fff, tt and quoted literals) and `o`, `s`, `u`, `d`, `D`; other tokens raise. Time zones in date functions are not supported (everything is UTC).

## Triggers

| ADF trigger | Output | Status |
|---|---|---|
| Schedule | `ScheduleDefinition`, **stopped**, cron from the recurrence (Minute, Hour, Day, Week, Month), Windows time zone names mapped for twelve common zones (others fall back to UTC with a note). Literal trigger parameters become run config, and a run started by the schedule reads `@trigger().scheduledTime` (the tick time, UTC) and `@trigger().startTime`; `@pipeline().TriggerType` is `ScheduleTrigger` and `TriggerName` the schedule's name. A run a person launches reads as a manual run with both times now. Recurrences that do not fit cron (every 7 minutes, every 2 weeks, last Friday, month days from the end) are refused with a reason and nothing is generated | cron conversion tested; schedules load and match in gate 3 |
| Tumbling window | the pipeline's asset becomes time-partitioned (`TimeWindowPartitionsDefinition`) with a schedule built from it, stopped. Windows are anchored to the trigger's `startTime` as the trigger page defines them (an hourly trigger starting 10:10 has windows at :10, a 6-hour one starting 03:00 at 03, 09, 15, 21; seconds are dropped), so the cron is built from the start minute and hour, not from midnight. Frequencies are Minute, Hour and Month (an hour interval that is a multiple of 24 is a day); windows that drift against the calendar (every 5 hours, every 7 minutes, a monthly start on day 29 to 31) are refused with a reason. The run gets `windowStartTime` and `windowEndTime` in UTC and the trigger's parameter expressions are evaluated at run time. `retryPolicy` becomes the asset's retry policy (delay at least 30 seconds, as documented). `maxConcurrency`, `delay` and `dependsOn` are reported, not enforced, and ADF's backfill of every window since `startTime` (oldest first) is reported as a difference: Dagster creates the latest window's run, so launch a backfill for the history | tested against the trigger page's examples; never run |
| Blob events, custom events and anything else | not generated; the unit is `unmapped` and the pipeline's questions ask what raises the event | no translation yet |

## Linked services and datasets

A linked service of type AzureSqlDatabase, SqlServer, AzureSqlDW, AzureSqlMI or AzureSynapseAnalytics used by a translated activity becomes the environment variable `ADF_CONN_<NAME>` (a SQLAlchemy URL you supply). A template that leaves the linked service to deploy time (`[parameters('X')]`) is handled by naming the connection after the parameter (`ADF_CONN_X`; for files, `ADF_FS_X`, with the store taken from the dataset's location type). Every other linked service is an `unmapped` unit. Secrets are dropped on load and counted in the unit's notes; a self-hosted integration runtime reference is recorded and raised as a network question. Datasets are folded into the activities that use them (table, schema; parameterised datasets are resolved at the call site).

## Known differences that apply to every pipeline

Independent activities run sequentially; activity timeouts are not enforced; schedules start stopped; global parameters come from `ADF_GLOBAL_<NAME>` environment variables; the output of a Web activity follows JSON-object responses, with `Response` for anything else.

## Verified against Microsoft's documentation

`tests/data/` holds the documentation pages this section rests on (CC BY 4.0, see its README). Each item is a test.

- **Every function example** in the expression reference (71 expression and result pairs, plus 49 more copied from the multi-expression examples) evaluates to the documented result, except those the documentation gets wrong, which are listed in `ERRATA` with the reason (for example `dayOfWeek('2018-03-15T13:27:36Z')` is documented as 3 although the page says Sunday is 0 and that day was a Thursday). Case sensitivity follows the pages: `contains` and `replace` are case-sensitive; `startsWith`, `endsWith`, `indexOf` and `lastIndexOf` are not. Functions the converter does not translate (`xml`, `xpath`, the binary conversions, object literals) stay stubs.
- **All 26 schedule recurrences** in the trigger reference convert to a cron expression Dagster accepts that fires as described: hours or minutes not listed come from the start time, but minutes without hours mean every hour; `monthDays: [-1]` is `L`; `monthlyOccurrences` are `d#n` and `Ld`; the third Friday from the end is refused.
- **Activity behavior:** `ExecutePipeline` waits by default; `ForEach` is parallel by default with `batchCount` 20 (maximum 50); `Until` has a 7 day default timeout and keeps looping when an inner activity fails; `Delete` is not recursive by default and a folder with no file name loses its files (or the folder too when recursive); `GetMetadata` with `exists` in the field list reports a missing path instead of failing; `Validation` with `childItems: false` waits for an empty folder; `Lookup` returns at most 5000 rows and fails over 4 MB; the Web activity times out after 1 minute unless `httpRequestTimeout` says otherwise and follows the `Location` header of a 202 response unless `turnOffAsync`.

- **Copy formats and mappings** (format, connector and schema-mapping pages): delimited text writes `\r\n` row delimiters by default and an empty field is null by default (`nullValue` is the empty string, so CSV to Parquet gives nulls and Parquet to CSV writes the sink's `nullValue`); the default mapping is by case-sensitive column name; an explicit mapping copies only the listed columns; ordinals start at 1 and name header-less columns `Prop_<n-1>`; a translator carrying only `typeConversion` settings is the default mapping (52 real Copy activities in the public corpus); a metadata-driven translator expression is resolved when the copy runs; the hierarchical-to-tabular example in the schema-mapping page produces its documented table.
- **Storage filters:** `*` matches zero or more characters, `?` zero or one, `^` escapes; `wildcardFolderPath` is read under the container and matched folder by folder; the four rows of the folder-and-file-filter table and the six `recursive` and `copyBehavior` rows are tests (flatten keeps readable names with a suffix on a clash, where ADF autogenerates names).
- **Script and SQL sinks:** a Script activity's output has the documented `resultSetCount`, `resultSets` and `recordsAffected`; its parameters are bound; upsert matches on `upsertSettings.keys`; `tableOption: autoCreate` creates the table; a stored-procedure source is called with its parameters.
- **Storage filters:** modified-time filters include the start and exclude the end; `deleteFilesAfterCompletion` is for binary copies only and removes each file after it was copied; `MergeFiles` joins the files into one; partition discovery turns `key=value` folders into columns. The Filter activity's output is `ItemsCount`, `FilteredItemsCount` and `Value`; the Web activity requires a JSON-object response; the Azure Function activity accepts GET, POST and PUT.
- **Data flows, from the public corpus:** a later transformation in a real flow reading a generated name is evidence of what ADF produces (two tests: pivot naming and the unpivot key column).
- **Data flows:** the function reference (101 example results run, 28 skipped because they need a type or format this executor refuses) and the transformation pages for aggregate, derived column, filter, join, select, sort, union, source and sink, exists, lookup, conditional split, surrogate key, rank and alter row.
