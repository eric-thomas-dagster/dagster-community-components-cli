# IBM Planning Analytics (TM1) → Dagster orchestration

**Goal:** wrap IBM Planning Analytics (TM1) with Dagster so you can schedule TI processes / chores, react to process state changes, materialize cube slices as DataFrame assets, and auto-emit assets for the entire cube + process catalog.

**Components used:**
- [`tm1_resource`](../../dagster-component-templates/tree/main/resources/tm1_resource) — shared TM1 REST auth (basic + CAM SSO)
- [`tm1_process_trigger_job`](../../dagster-component-templates/tree/main/jobs/tm1_process_trigger_job) — execute a TI process or chore
- [`tm1_process_status_sensor`](../../dagster-component-templates/tree/main/sensors/tm1_process_status_sensor) — event-drive on process status
- [`tm1_cube_data_ingestion`](../../dagster-component-templates/tree/main/assets/ingestion/tm1_cube_data_ingestion) — cube slice via MDX as a DataFrame
- [`tm1_workspace`](../../dagster-component-templates/tree/main/integrations/tm1_workspace) — **StateBackedComponent** — auto-emit one asset per (Cube, Process, Chore)

## One-command demo

Spins up a mock TM1 server in Docker (Flask container, ~130 MB), scaffolds a Dagster project, wires all five components, materializes end-to-end. **Costs $0** — no TM1 license needed.

```bash
curl -fsSL https://raw.githubusercontent.com/eric-thomas-dagster/dagster-community-components-cli/main/examples/setup_tm1_demo.sh \
  -o setup_tm1_demo.sh
bash setup_tm1_demo.sh
```

Output ends with the mock server URL (default `http://localhost:5495`) and instructions to run `dg dev`.

Once the UI is up (`http://localhost:3000`):

1. **Trigger a TI process** — Jobs → `run_gl_load` → **Launchpad** → **Launch Run**. Mock returns `CompletedSuccessfully` with the parameters echoed.
2. **Materialize `sales_by_product_period`** — the cube data ingestion emits a DataFrame with rows for Period × Product combinations (Jan/Feb/Mar × ProductA/ProductB).
3. **Toggle the status sensor** — Sensors → `gl_load_done` → **Start**. Polls every 30s; when process hits `CompletedSuccessfully`, triggers the reload job.
4. **See workspace-emitted assets** — `tm1/cube/Sales`, `tm1/cube/Finance`, `tm1/process/LoadActualsFromGL`, `tm1/process/RefreshHeadCountCube`, `tm1/chore/DailyRebuild` — auto-generated by enumerating the mock's catalog. Note: `TestCube` and `LegacyReport_deprecated` are filtered out by the selectors in `defs.yaml`.
5. **Materialize a process asset** — click `tm1/process/LoadActualsFromGL` → **Materialize**. Executes the underlying TI process via REST, polls to terminal status.

## Swap the mock for a real TM1 server

Three env vars change — everything else stays the same:

```bash
export TM1_URL="https://tm1.acme.com:5495"    # include port
export TM1_USER="your_user"
export TM1_PASSWORD="your_pass"
# For Cognos CAM SSO — set the namespace env var and reference it in the resource YAML:
# export TM1_CAM_NS="LDAP"
```

Then edit the resource's `defs.yaml` to add `cam_namespace_env_var: TM1_CAM_NS` for CAM SSO deployments.

## Common production patterns

### Nightly GL data load, then downstream dbt

```yaml
type: dagster_community_components.TM1ProcessTriggerJobComponent
attributes:
  job_name: nightly_gl_load
  target_type: process
  target_name: LoadActualsFromGL
  parameters:
    pYear: "2026"
    pMonth: "07"
  resource_key: tm1_resource
  wait_for_completion: true
  schedule: "0 4 * * *"
  default_status: RUNNING
```

Pair with a `tm1_process_status_sensor` targeting `CompletedSuccessfully` → triggers your dbt-refresh job.

### Ingest a planning cube slice into Snowflake

```yaml
# 1. Read cube slice
type: dagster_community_components.TM1CubeDataIngestionComponent
attributes:
  asset_key: forecast_actuals
  cube: Finance
  mdx: |
    SELECT
      NON EMPTY [Period].Members ON ROWS,
      NON EMPTY [Account].Members ON COLUMNS
    FROM [Finance]
    WHERE ([Version].[Actual], [Year].[2026])
  resource_key: tm1_resource
```

Chain downstream `dataframe_to_snowflake` for BI dashboards.

### Auto-emit every process as a Dagster asset

```yaml
type: dagster_community_components.TM1WorkspaceComponent
attributes:
  base_url_env_var: TM1_URL
  username_env_var: TM1_USER
  password_env_var: TM1_PASSWORD
  process_selector:
    by_pattern: [Load_*, Refresh_*]
  group_name: tm1_operations
  defs_state:
    management_type: LOCAL_FILESYSTEM
    refresh_if_dev: true
```

Every matching TI process becomes a Dagster asset. Materialize any of them from the UI to run the process — Dagster tracks execution history + run metadata automatically.

## TM1 vs Cognos vs. Fivetran / DBT

- **TM1** = planning cubes (this integration). Multidimensional writeback, budgeting, forecasting, consolidation.
- **Cognos Analytics** = BI dashboards + reports (separate `cognos_workspace` integration).
- **Fivetran / Airbyte** = SaaS ELT. Not what TM1 does.
- **DBT** = SQL modeling on your warehouse. Common downstream: TM1 → warehouse → dbt.

Use this integration when TM1 is already deployed and you want Dagster as the orchestration control plane.
